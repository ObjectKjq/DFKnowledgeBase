# P0 文件权限与回收站实施记录

对应 [Issue #19](https://github.com/ObjectKjq/DFKnowledgeBase/issues/19)，规格故事 1～15、30～37。后端继续使用真实 MySQL、Sa-Token、现有公共错误与分页契约。

## 行为

- 上传记录 `uploader_id`；未关联文件只允许上传者读取、关联和删除。关联后按当前知识库内容权限判定，上传者与实例管理员没有额外内容访问权。查看者能读取，但不能把原文件关联到其他知识库；有内容写入权限的用户可以关联。
- 文件删除入口拒绝仍有业务引用的文件，业务删除必须经过文档回收站。文档和知识库的手动彻底删除要求 `confirmed=true`；保留期内的软删除引用继续保护文件字节。最后一个保留引用移除后，物理删除文件元数据与 `LONGBLOB` 行。
- 知识库用 `delete_time` 表示业务回收站，正常列表、成员访问与文件读取立即排除已删除知识库。原所有者可在删除时间加 30 天之前恢复，并保留成员。原可用文档进入索引中，原处理中重新排队，原失败文档保留失败及原因，独立文档回收站状态保持不变。
- 文档恢复在行锁内校验保留期并显式清空删除字段，提交后启动处理。达到删除时间加 30 天时不可恢复，自动清理条件与此一致。
- `DocPurgeJob` 每天凌晨 3 点先清理超期知识库，再清理超期文档。保留历史会话及答案，不删除历史消息。
- 业务关联与字节回收共用文件行锁；引用回收使用当前加锁读取，避免 MySQL REPEATABLE READ 旧快照遗漏刚提交的业务引用。文档创建持有知识库生命周期锁，避免知识库彻底删除后产生孤立文档。

新增接口及参数以 Controller 的 OpenAPI 注解为准，同目录 `.http` 提供恢复、回收站和确认彻底删除示例。

## 存量升级

已有部署在启动新版应用前执行一次 `sql/upgrade/012-content-lifecycle.sql`，新部署使用 `sql/schema.sql`。升级保留存量业务内容，按可信数字 `creator` 补上传者，恢复仍被保留文档引用的文件逻辑标记，并将旧逻辑删除知识库转入带删除时间的回收站。

无可信上传者且没有业务引用的历史文件保持不公开，不自动分配给管理员。旧版本删除知识库时已经删掉的成员关系没有可信的删除原因，无法区分主动移除和随知识库删除，不擅自复活历史成员；仍存在的成员关系以及新版软删除保留的关系能够恢复。
