# 入库管线用 Spring 线程池 + MySQL 状态机，不引入 MQ

> 2026-10-22 评审补充：同一知识库默认并发 1、全实例默认并发 2，管理员可调整；待处理任务按提交顺序持久保存，线程池队列满时不丢任务、不由上传请求代为解析。服务重启后继续调度。实现仍采用 MySQL 状态机与线程池，不引入 MQ；当前实现尚需补齐持久化调度约束。

FR-3 的「排队 → 解析中 → 索引中 → 可用/失败」需要异步执行、失败重试与重启恢复。本工程是单 Maven 模块单机部署（ADR-0001/0003），没有 MQ 依赖，为入库任务引入 MQ 与部署形态不符。采用 Spring `ThreadPoolTaskExecutor` 异步执行入库任务，文档表的状态列即任务状态机；服务启动时把停留在「排队/解析中/索引中」的文档重新入队；「失败」由用户显式重试（FR-3）。

**Considered Options**：

- 引入 RabbitMQ/Kafka 做任务队列：多一个中间件、单机部署收益低；被否决。
- Spring Batch：面向批处理作业，对「逐文档上传→异步加工」的在线场景过重；被否决。
- 线程池 + MySQL 状态机：被采纳。

**Consequences**：并发度由线程池参数控制（单库同时处理任务数上限见 PRD §8.4）；队列在进程内，不支持多实例横向扩展——单机形态下可接受；文档状态直接可查（前端轮询展示进度）；入库吞吐受进程内向量化（ADR-0008）制约。
