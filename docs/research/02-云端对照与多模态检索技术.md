# 云端 SaaS 知识库/AI 问答产品对照与多模态检索技术专项调研

> 调研目的：为「可本地化部署的知识库平台」（支持关键字、图片、向量搜索与 RAG，提供网页客户端与 MCP 服务端，目标用户为学生与工作者）提供竞品借鉴与功能扩展素材。
> 调研范围：第一部分覆盖 Google NotebookLM、Notion AI、Glean、Mem、微软 Copilot、腾讯 ima.copilot、飞书知识库/知识问答（云端产品仅做简要对照）；第二部分覆盖图片搜索、多模态文档解析、向量库/混合检索栈、2025–2026 RAG 新趋势四个技术专项。
> 信息源优先级：官方文档 / 官网 / 官方博客 > 论文原文 > 权威技术社区。调研时间：2026-10。云端产品功能演化快，引用信息请以页面当前状态为准。

### 二、亮点提炼（可借鉴清单）

#### 1. Google NotebookLM
- **音频概览（Audio Overviews）**：把用户来源转成双主持人播客式对谈，且支持交互模式——用户可以中途插话提问、深入讨论；后来扩展出 Brief、Debate 等多种输出格式与 Video Overviews（[官方博客](https://blog.google/innovation-and-ai/models-and-research/google-labs/notebooklm-student-features/)、[NotebookLM Plus 商用技巧](https://blog.google/innovation-and-ai/models-and-research/google-labs/notebooklm-business-tips/)）。**借鉴点**：知识库内容的「多模态消费」（听/看）是低成本高感知的差异化功能。
- **来源本位 + 引用溯源**：所有回答严格限定在用户上传来源内，逐句引用可回跳原文，是其最强信任设计。**借鉴点**：RAG 答案默认「引用到块级/页级」并可一键跳转原文。
- **来源发现（Discover sources）**：帮助用户向知识库补充新资料（[官方德语博客：来源发现与多语言音频](https://blog.google/intl/de-de/unternehmen/technologie/notebooklm-audio-zusammenfassungen/)）。**借鉴点**：知识库的「主动推荐补充资料」能力。
- **多语言本地化**：音频/视频概览已支持 50+ 乃至 80 种语言（[官方博客](https://blog.google/technology/google-labs/notebooklm-audio-overviews-50-languages/)）。

#### 2. Notion AI
- **Enterprise Search**：一次提问跨工作区与 Slack、Google Drive、Jira 等已连接应用统一找答案，回答**永远附来源**，可回溯到原始应用（[官网](https://www.notion.com/product/enterprise-search)、[帮助中心](https://www.notion.com/en-us/help/enterprise-search)）。**借鉴点**：「连接器 + 统一索引 + 逐答案引用」的检索体验标准。
- **Research Mode**：自动分析工作内容与全网来源，生成可保存、可分享的详细报告（[官网](https://www.notion.com/product/enterprise-search)）。**借鉴点**：从「问答」升级到「生成研究报告」的输出形态。

#### 3. Glean
- **企业统一搜索 + 知识图谱**：275+ 权限感知连接器把内容、活动信号、权限集归一进统一数据层，喂给 Knowledge Graph，支撑 Search、Chat（RAG）与 Agent，支持 indexed / live-retrieval / hybrid 多种接入（[连接器文档](https://docs.glean.com/connectors/connectors-power-glean)）。**借鉴点**：权限随内容入索引（permissions-aware indexing）是企业知识库的安全底座。
- **混合检索排序**：语义搜索 + 关键字匹配 + 图谱排序三路融合，再用 RAG 生成答案，「每个答案都可追溯、可验证」（[官方对比文](https://www.glean.com/perspectives/comparing-glean-features-and-chatgpt-enterprise-capabilities)）。**借鉴点**：BM25 + 向量 + 元数据/图谱信号的多路召回 + RAG 引用闭环。
- **专用小型检索模型**：为 agentic search 与自适应推理训练专用小模型以降低 token 消耗（[官网对比页](https://www.glean.com/compare/glean-vs-claude-enterprise)）。**借鉴点**：检索/重排环节用小模型、生成环节用大模型的成本结构。

#### 4. Mem
- **AI 自动组织**：Collections 按内容与上下文自动归类连接笔记，「不必再想放哪里」（[Collections 博文](https://get.mem.ai/blog/organize-your-notes-with-ai-using-collections)、[帮助中心](https://help.mem.ai/)）；Spaces 自动分区（联系人/待办/想法/项目）（[官网](https://www.usemem.com/)）。**借鉴点**：知识库自动打标/自动归档/智能文件夹。
- **对话即写入**：对 Mem 说一句话，它自动找到或创建正确的笔记并更新（[Chat 功能页](https://get.mem.ai/features/chat)）。**借鉴点**：MCP/对话入口直接沉淀知识（创建/更新笔记）而不只是读。
- **语义合并重构**：按语义（而非字面）合并冗余笔记、清理知识库「腐烂」（[AI 重构知识库博文](https://get.mem.ai/blog/ai-knowledge-base-refactoring)）。**借鉴点**：知识库治理工具（去重、合并、清理）。

#### 5. 微软 Copilot
- **语义索引（Semantic Index）**：把组织数据映射到高级词法 + 语义双索引，结合 Microsoft Graph 的上下文与关系提升检索精度，并全程尊重租户权限边界（[Microsoft Learn](https://learn.microsoft.com/en-us/Microsoftsearch/semantic-index-for-copilot)）。**借鉴点**：词法 + 语义双索引 + 权限边界。
- **Copilot connectors**：把业务系统数据摄入 Graph 作为 grounding 依据，跨 M365 复用（语义索引、引用）（[知识源文档](https://learn.microsoft.com/pl-pl/microsoft-365/copilot/extensibility/knowledge-sources)、[Copilot Studio 对比文档](https://learn.microsoft.com/is-is/microsoft-copilot-studio/knowledge-graph-vs-power-platform-connectors)）。**借鉴点**：「索引进知识层」与「实时 API 调用」两类连接器的分工设计。

#### 6. 腾讯 ima.copilot
- **微信生态剪藏闭环**：本地文件、微信文件、公众号文章、网页、图片、音频多形态入库，搜索结果/网页一键收藏进知识库（早期每用户 1GB 空间）（[澎湃实测](https://www.thepaper.cn/newsDetail_forward_29179630)、[功能梳理](https://m.wandoujia.com/apps/8435540)）。**借鉴点**：低摩擦采集入口（浏览器插件/剪藏/IM 转发）是个人知识库增长关键。
- **共享知识库 + 小程序**：知识库可共享多人使用，微信小程序里直接导入文件、分享/加入知识库并基于知识库或全网 AI 问答（[环球网](http://m.toutiao.com/group/7454080907025318441/)）。**借鉴点**：知识库的共享与协作消费场景。
- **copilot Agent 化**：记忆系统持续学习用户偏好，直接读取知识库内文件/笔记跨文件汇总整理，支持官方外模型自由接入（[ima copilot 发布说明](https://view.inews.qq.com/a/20260525A03F0K00)）。**借鉴点**：知识库作为 Agent 的执行素材（跨文件汇总/生成），而非仅检索。

#### 7. 飞书知识库 / 知识问答
- **知识库内嵌问答入口（问问知识库）**：知识库管理员可开启/关闭并配置推荐问题，用户在知识库内直接提问，基于当前知识库内容生成答案（[帮助中心](https://www.feishu.cn/hc/zh-CN/articles/138181848717-%E8%AE%BE%E7%BD%AE%E7%9F%A5%E8%AF%86%E5%BA%93%E7%9A%84%E7%9F%A5%E8%AF%86%E9%97%AE%E7%AD%94%E5%8A%9F%E8%83%BD)、[知识库中使用知识问答](https://www.feishu.cn/hc/zh-CN/articles/143241168260-%E5%9C%A8%E7%9F%A5%E8%AF%86%E5%BA%93%E4%B8%AD%E4%BD%BF%E7%94%A8%E7%9F%A5%E8%AF%86%E9%97%AE%E7%AD%94)）。**借鉴点**：「每个知识库一个问答机器人」的细粒度产品形态。
- **权限过滤问答**：知识问答只基于用户有权限访问的消息、文档、知识库作答（[使用知识问答](https://www.feishu.cn/hc/zh-CN/articles/854453754409-%E4%BD%BF%E7%94%A8%E7%9F%A5%E8%AF%86%E9%97%AE%E7%AD%94)）；并可勾选**联网搜索**混合外部信息（[知识库中使用知识问答](https://www.feishu.cn/hc/zh-CN/articles/143241168260-%E5%9C%A8%E7%9F%A5%E8%AF%86%E5%BA%93%E4%B8%AD%E4%BD%BF%E7%94%A8%E7%9F%A5%E8%AF%86%E9%97%AE%E7%AD%94)）。**借鉴点**：RAG 检索阶段做 ACL 过滤 + 「知识库优先、联网兜底」的混合问答。

### 三、小结：共性与差异

- **共性**：头部产品普遍做到「检索即答 + 逐答案引用溯源」；企业向产品（Glean、Copilot、飞书）把**权限感知**做进检索链路；个人向产品（NotebookLM、ima、Mem）把**采集入口与内容再消费**（音频/小程序/自动整理）做到极致。
- **差异**：云端 SaaS 的图片搜索普遍偏弱（多为文档内 OCR/解读而非以图搜图），RAG 索引以文本为主——这是本地化产品可在多模态检索上形成差异化的空间（见第二部分）。
- **对本产品的直接启示**：① 答案引用溯源到块/页级并可跳转；② 权限随内容入索引；③ 低摩擦采集入口（剪藏/微信/浏览器）；④ 知识库内嵌问答 + MCP 对外供给（对标 Outline `/mcp` 的接入体验）；⑤ 内容多模态消费（音频概览）作为进阶功能。

## 第二部分：多模态检索技术专项

### 1. 图片搜索的主流实现

#### 1.1 以文搜图 / 以图搜图：多模态 Embedding（CLIP / SigLIP 系）

- **原理**：图文双编码器（image encoder + text encoder）经对比学习映射到同一向量空间，匹配对靠近、非匹配对远离；训练数据为 4 亿图文对（CLIP，[论文：Learning Transferable Visual Models From Natural Language Supervision](https://ar5iv.org/abs/2103.00020)）。查询时把文本或图片编码成向量做 ANN 检索，天然同时支持**以文搜图**与**以图搜图**（同一向量场），[CLIP 原理解析](https://intuitivepapers.ai/clip/)。
- **SigLIP**：用成对 sigmoid loss 把图文匹配变成独立二分类，去掉 softmax 全局归一化，小批量下更好、可扩展更大批量（[论文：Sigmoid Loss for Language Image Pre-Training](https://arxiv.org/pdf/2303.15343)）；SigLIP 2 进一步提升多语言、定位与稠密特征能力（[论文：SigLIP 2](https://arxiv.org/pdf/2502.14786)）。
- **工程现状**：CLIP（ViT-L/14）仍是部署最广、生态最深的「安全默认项」，但已非 SOTA；SigLIP 等在细粒度视觉匹配、多语言自托管场景更受推荐（[多模态 embedding 模型横评](https://mixpeek.com/curated-lists/best-multimodal-embedding-models)、[图像 embedding 模型对比](https://www.edenai.co/post/best-image-embeddings)）。多语言场景可关注 jina-clip 类「文本+图片」双塔统一模型（[Jina CLIP-V2 论文](https://arxiv.org/pdf/2412.08802v1.pdf)）。
- **优缺点**：
  - 优点：一套索引同时支持文搜图/图搜图；零样本能力强，无需标注训练；与向量库天然兼容（[RAG 图像索引架构说明](https://c13n.club/blog/2026-06-02/index.pdf)）。
  - 缺点：对**图内文字、数字、专有名词**不敏感（视觉 embedding 不擅长精确字符匹配）；细粒度/局部匹配弱（全局向量）；纯 CLIP 对中文长文本查询效果一般，需多语言版或配合文本 embedding。

#### 1.2 图片内文字 OCR 后索引

- **原理**：对图片/截图/扫描件跑 OCR，把识别出的文字作为普通文本进入 BM25/向量索引，图片作为该文本块的「载体」返回。企业检索产品典型实现如 Azure AI Search：用 OCR skill 提取图中文字（如 STOP 标志上的词），再与图像分析生成的文本描述（caption）一起入索引（[Microsoft Learn：Extract Text from Images](https://learn.microsoft.com/fil-ph/azure/search/cognitive-search-concept-image-scenarios)）。
- **优缺点**：
  - 优点：精确关键字匹配（编号、人名、公式、表格内文字）远强于纯视觉向量；实现简单、可复用文本检索/高亮/引用链路；对知识库中大量截图、PPT、扫描笔记场景价值高。
  - 缺点：只覆盖「有文字」的图片，纯视觉内容（图表、照片、示意图语义）搜不到；OCR 有识别误差；版面/表格结构丢失（需结构化解析补足，见 §2）。

#### 1.3 Caption / VLM 描述索引与组合方案

- **原理**：用 VLM 给图片生成自然语言描述（caption），与 OCR 文本、多模态向量一起索引；多模态 RAG 的典型栈是「多模态 embedding + 向量库 + 多模态 LLM 生成」三件套（[多模态 RAG 端到端教程](https://asoasis.tech/articles/2026-04-11-0853-multi-modal-rag-images-text-tutorial/)、[Visual RAG 管线组件](https://www.codecademy.com/article/rag-with-llama-3-2)）。生产级方案通常把页面、caption、版面元数据、embedding 分开存储并统一检索（[LanceDB Multimodal RAG](https://lancedb.com/lp/rag-hybrid-search)）。
- **推荐组合（三路互补）**：**多模态向量（CLIP/SigLIP）** 负责语义级文搜图/图搜图 + **OCR 文本** 负责图内精确文字命中 + **caption** 负责自然语言描述检索，三路结果用 RRF 融合（见 §3），命中后可把图片直送多模态 LLM 做 grounded 回答（[多模态 RAG 教程](https://asoasis.tech/articles/2026-04-11-0853-multi-modal-rag-images-text-tutorial/)）。

**选型要点**：
- 传统「解析→分块→文本索引」路线：中文/公式优先 **MinerU**，通用文档默认 **Docling**，需要管道编排/多源连接器用 **Unstructured**，扫描件 OCR 底座选 **PaddleOCR** 或 **Surya**；混合语料可按元数据/分类器路由解析器（[Docling/Marker/MinerU 生产实践指南](https://www.spheron.network/blog/self-host-document-intelligence-docling-marker-mineru-rag-guide/)、[PDF 解析工具评测](https://nbrosse.github.io/posts/pdf-parsing/pdf-parsing.html)）。
- 视觉 RAG 路线（**ColPali/ColQwen**）：文档整页图像向量化 + MaxSim 检索，对图表/扫描件/复杂版面效果好、架构更简单，但多向量存储开销大、纯文本精确匹配（编号/引用）仍需文本索引兜底（[ColPali 论文](https://arxiv.org/html/2407.01449v6)、[视觉文档检索解析](https://mixpeek.com/visual-document-retrieval)）。
- **实践建议**：文本解析路线为主（可检索、可引用、成本低），ColPali 类页面向量作为图表/扫描件的「第二索引」，两路融合；图片另行走 §1 的多模态向量 + OCR + caption 三路索引。

### 3. 向量库 / 检索栈对混合检索与多模态的支持

|---|---|---|---|---|
| **Qdrant** | 稀疏+稠密向量、payload 过滤，单二进制/Docker 轻部署 | 官方多模态教程（FastEmbed/CLIP/Cohere Embed 4 同一向量场文搜图/图搜图） | 支持融合与 rerank（可外挂） | [Qdrant 多模态搜索教程](https://qdrant.tech/documentation/tutorials-basics/multimodal-search/)、[Cloud Inference（CLIP 示例）](https://qdrant.tech/documentation/inference/cloud-inference/)、[多模态 RAG 教程](https://qdrant.tech/documentation/advanced-tutorials/multimodal-search-fastembed/) |

| **pgvector** | 与 PostgreSQL 全文检索（tsvector/BM25 扩展）同库并存，可 SQL 级融合 | 存储任意 embedding（含图片向量） | 需应用层做 RRF/rerank | [pgvector 文档](https://access.crunchydata.com/documentation/pgvector/0.8.1/pdf/pgvector.pdf)、[pgvector 0.8.0 发布](https://www.postgresql.org/about/news/pgvector-080-released-2952/) |

**关键机制**：
- **RRF（Reciprocal Rank Fusion）**：按各路结果的**排名倒数**（而非原始分数）融合，天然规避 BM25 分数与向量相似度量纲不可比的问题，几乎免调参，是混合检索的推荐起点；代价是丢弃分数幅度信息（[Elastic RRF 文档](https://www.elastic.co/docs/reference/elasticsearch/rest-apis/reciprocal-rank-fusion)、[Elasticsearch Labs 最佳实践](https://www.elastic.co/search-labs/cn/blog/vector-search-best-practices-elasticsearch)、[Milvus RRFRanker](https://milvus.io/docs/zh/v2.5.x/reranking.md)）。
- **Rerank 模型**：候选集合并后用交叉编码器精排。**bge-reranker-v2-m3**（BAAI，568M、多语言、易部署、推理快，基于 bge-m3）是本地化部署的主流选择（[BGE Reranker v2 文档](https://bge-model.com/bge/bge_reranker_v2.html)、[ModelScope 模型页](https://modelscope.cn/models/BAAI/bge-reranker-v2-m3)、[智源发布博文](https://hub.baai.ac.cn/view/35966)）；更强可选 jina-reranker-v3 等 late-interaction 精排模型（[jina-reranker-v3 论文](https://arxiv.org/pdf/2509.25085v1)）。
- **BGE 全家桶互补**：bge-m3 向量模型本身支持「文本+图片」混合检索与多语言/长文本，与 reranker 配套（[BGE 官方页](https://bge.baai.ac.cn/)、[智源博文](https://hub.baai.ac.cn/view/35966)）。
- **对本产品**：本地化单机优先考虑 **LanceDB（嵌入式、FTS+向量+rerank 一体、多模态友好）或 Qdrant（单二进制、稀疏+稠密）**；已有 PostgreSQL 可用 pgvector 减少组件；重检索质量则「BM25+向量双路 → RRF → bge-reranker-v2-m3 精排」三段式。

### 4. 2025–2026 RAG 新趋势

#### 4.1 Agentic RAG
- 把自主 Agent 的**反思、规划、工具调用、多智能体协作**引入 RAG 流水线，动态管理检索策略、迭代精炼上下文、按任务自适应工作流，超越静态「一次检索一次生成」（[Agentic RAG 综述](https://arxiv.org/html/2501.09136v1)）。
- 后续演进为 **Reasoning Agentic RAG**：区分「预定义编排的推理」与「动态自主决策的推理」两类范式，检索与模型驱动的规划/自我反思/工具使用融合（[Reasoning RAG 综述](https://arxiv.org/html/2506.10408)）；更激进的方向如 Interact-RAG 让 LLM Agent 主动操纵语料与检索过程（动作原语控制检索粒度）（[Interact-RAG 论文](https://arxiv.org/html/2510.27566v1)）。
- **对本产品**：MCP 服务端天然契合 Agentic RAG——把「关键字/向量/图片检索、rerank、知识库写入」暴露为 MCP 工具，让 Codex/Trae 等 Agent 自主决定检索策略（多跳、改写、混合）；产品内也可做查询分类 → 检索路由。

#### 4.2 GraphRAG
- 微软 GraphRAG：从原始文本抽取知识图谱 → 构建社区层级 → 生成社区摘要，检索时用图结构增强 RAG；查询引擎提供 **Local Search**（实体邻域+原文块）、**Global Search**（社区摘要+全局归纳）、**DRIFT Search**（Local+Global 结合）与 Basic Search 四种模式（[GraphRAG 官方文档](https://microsoft.github.io/graphrag/?categoryid=2849243)、[Query Engine 概览](https://microsoft.github.io/graphrag/query/overview/)、[Microsoft Research 发布博文](https://www.microsoft.com/en-us/research/blog/graphrag-new-tool-for-complex-data-discovery-now-on-github/)）。
- **对本产品**：适合「跨文档多跳问答」「整库综述类问题」（如「我这学期所有笔记里反复出现的概念」）；缺点是建图成本高（大量 LLM 调用），可作为可选高级索引而非默认路径。

#### 4.3 上下文检索（Contextual Retrieval）
- Anthropic 提出：分块前给每个 chunk 用 LLM 补写一段「所属文档的上下文说明」再做 embedding/BM25 索引，缓解 chunk 断章取义导致的检索失败；配合 **Contextual BM25** 效果更佳（[Anthropic 官方介绍](https://www.anthropic.com/news/contextual-retrieval)）。
- 成本问题靠 **prompt caching** 解决：整篇文档只入缓存一次，逐 chunk 引用缓存内容生成上下文，成本可降一个量级；且上下文化是**入库时一次性成本**，不增加查询时延（[Prompt caching 文档](https://platform.claude.com/docs/en/build-with-claude/prompt-caching)、[Contextual Embeddings 指南](https://platform.claude.com/cookbook/capabilities-contextual-embeddings-guide)）。
- **对本产品**：本地化部署可改用本地小模型做 chunk 上下文化（离线批处理）；对知识库「分块后互相隔离」的痛点（表格续页、代词指代）性价比极高，值得列为入库管线可选项。

#### 4.4 端侧小模型嵌入
- **EmbeddingGemma**（Google，2025-09 开源）：308M 参数、基于 Gemma 3 的多语言文本嵌入模型，专为手机/笔记本/平板优化，支持离线 RAG、语义搜索、分类聚类；支持 Matryoshka 表示学习（可截断维度换质量/体积）（[官方模型概览](https://ai.google.dev/gemma/docs/embeddinggemma?hl=zh-CN)、[论文](https://arxiv.org/pdf/2509.20354)、[InfoQ 报道](https://www.infoq.com/news/2025/09/embedding-gemma/)），是 MTEB 上 500M 以下多语言文本嵌入的领先开源模型（[HyperAI 报道](https://hyper.ai/en/stories/ccebf2393a423969af4debfcd1a622d6)）。
- **趋势含义**：embedding/rerank 环节的模型小型化使「完全本地、可离线」的知识库检索成为现实——Joplin（约 140MB 本地模型）等已内置离线语义搜索（见姊妹篇《03-自托管笔记知识管理工具调研》），SigLIP/Surya/PaddleOCR-VL 等视觉/OCR 模型也都在 1B 以下量级可本地跑（[Surya OCR 2](https://www.datalab.to/blog/surya-2)、[PaddleOCR-VL](https://www.paddleocr.ai/main/en/version3.x/algorithm/PaddleOCR-VL/PaddleOCR-VL.html)）。
- **对本产品**：默认采用端侧/本地小模型（EmbeddingGemma、bge-m3、bge-reranker-v2-m3）保证离线与隐私，同时保留 OpenAI 兼容 embedding API 可切换云端大模型；利用 Matryoshka 降维在低配设备上平衡质量与内存。

#### 4.5 趋势小结

| 趋势 | 核心价值 | 落地优先级建议 |
|---|---|---|
| Agentic RAG | 检索策略自适应、多跳、工具化 | 高：以 MCP 工具面承接，Agent 侧自动受益 |
| GraphRAG | 跨文档多跳、全局综述问答 | 中：可选高级索引，按需建图 |
| Contextual Retrieval | 修复分块断章取义，检索质量普惠性提升 | 高：入库管线可选项，成本低收益直接 |
| 端侧小模型嵌入 | 完全离线、隐私、零 API 成本 | 高：本地化部署的核心支撑 |

## 结论

1. **产品层**：借鉴 NotebookLM 的引用溯源与音频概览、Glean 的权限感知混合检索、ima 的低摩擦剪藏入口、飞书的「知识库内嵌问答 + ACL 过滤」、Mem 的自动整理，形成「采集—检索—问答—沉淀」闭环。
2. **技术层**：推荐主线为「多格式解析（MinerU/Docling/PaddleOCR）→ 文本 + 图片三路索引（BM25/向量/OCR+caption）→ RRF 融合 → bge-reranker-v2-m3 精排 → 带引用生成」；ColPali 页面向量、GraphRAG、Contextual Retrieval 作为进阶扩展，embedding/rerank 全部走本地小模型以满足离线私有化。
3. **差异化**：云端 SaaS 图片搜索普遍薄弱，「以文搜图 + 以图搜图 + 图内文字检索」三合一与 MCP 供给是本地化产品的可行差异点。
